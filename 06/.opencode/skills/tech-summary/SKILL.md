# 技术内容深度分析技能

## 使用场景

- 需要对 `knowledge/raw/` 中的采集数据进行深度分析和总结
- 需要提炼技术亮点、评分、趋势发现
- 需要生成结构化的分析结果供知识库使用

## 执行步骤

### 1. 读取最新采集文件

使用 Glob 查找 `knowledge/raw/` 目录下最新的文件：

```
knowledge/raw/*.json
```

按文件名中的日期降序排列，取最新一个文件进行读取。若无文件则终止并提示用户先执行数据采集。

### 2. 逐条深度分析

对每个项目进行以下分析：

#### 摘要

撰写一句话中文摘要，不超过 50 字，遵循公式：

> **项目名 + 核心能力 + 关键价值**

示例："LangGraph — 构建有状态多步 Agent 的框架，循环图结构支持复杂工作流编排"

#### 技术亮点

列出 2-3 个亮点，要求用事实说话：

- 具体技术特性或架构决策，而非空泛形容词
- 优先引用仓库 README 或代码中的关键技术细节

示例：
- "采用 DAG 调度引擎，支持节点级失败重试"
- "内置 OpenTelemetry 链路追踪，可观测性强"

#### 评分

按以下标准打分（1-10）：

| 分段 | 含义 | 说明 |
|------|------|------|
| 9-10 | 改变格局 | 开创全新范式或大幅降低门槛，行业级影响力 |
| 7-8 | 直接有帮助 | 解决明确痛点，可直接投入生产使用 |
| 5-6 | 值得了解 | 有参考价值但尚未成熟或适用范围有限 |
| 1-4 | 可略过 | 低质量、重复或与目标领域关联极弱 |

每个评分必须附带 1-2 句理由。

#### 标签建议

为每个项目推荐 3-5 个标签，使用英文小写连字符格式（如 `large-language-model`）。

### 3. 趋势发现

跨项目横向分析，提炼：

- **共同主题**：多个项目共同关注的技术方向
- **新概念**：首次出现或快速兴起的技术概念

示例：
- 共同主题："本地化推理" —— 多个项目强调端侧部署和隐私保护
- 新概念："Agentic RAG" —— 将 Agent 决策能力融入检索增强生成

### 4. 输出分析结果

将分析结果写入 JSON 文件，路径：`knowledge/raw/github-trending-{YYYY-MM-DD}-enriched.json`

```json
{
  "date": "2026-05-12",
  "source": "tech-summary",
  "analyzed_at": "2026-05-12T14:00:00Z",
  "trends": {
    "common_themes": ["本地化推理", "多模态融合"],
    "emerging_concepts": ["Agentic RAG"]
  },
  "items": [
    {
      "id": "",
      "full_name": "owner/repo",
      "summary": "一句话中文摘要（≤50字）",
      "highlights": [
        "基于 DAG 的多步任务编排",
        "内置断点恢复与重试机制"
      ],
      "score": 8,
      "score_reason": "解决 Agent 工作流编排痛点，可直接用于生产环境",
      "tags": ["agent", "workflow", "orchestration"],
      "html_url": "https://github.com/owner/repo",
      "language": "Python",
      "stargazers_count": 12345
    }
  ]
}
```

## 评分约束

- 15 个项目中，评分 9-10 分的项目不超过 **2 个**
- 9-10 分必须给出充分的"改变格局"理由，避免通胀
- 若整体质量偏低，允许 9-10 分名额空缺

## 注意事项

- **信息来源**：摘要和分析必须基于仓库官方信息，不得编造功能或数据. 确保摘要不超过 50 字，超出则精简
- **客观性**：趋势分析应客观中立，避免过度吹捧或贬低, 技术亮点必须基于事实（代码特性、架构决策、性能数据），禁止使用"强大""优秀"等空泛描述
- **评分标准**：`relevance_score` 根据与 AI/LLM/Agent 的直接相关度、技术成熟度、社区活跃度综合评定，评分理由需具体，避免"很有潜力"之类笼统表述
- **标签规范**：标签使用英文小写，用连字符分隔，避免过于宽泛的标签（如 `ai` 太泛，应使用更具体的 `agent-framework`）
- **字符编码**：所有文本保持 UTF-8，中文摘要不要转义
- **幂等性**：如果 enriched 文件已存在，读取后更新，不要完全覆盖（保留已有分析结果，仅更新新增条目）
- **网络问题**：访问仓库详情时如遇网络问题，可基于已有信息进行分析，但需在分析中注明信息有限
- **语言约定**：摘要、分析使用中文；标签、JSON 键名、技术术语保留英文

## 质量检查清单

分析完成后，逐条检查：

- [ ] 每个条目都有 `summary`，且不超过 50 字
- [ ] 每个条目有 2-3 个基于事实的技术亮点
- [ ] 每个条目有评分及理由
- [ ] 9-10 分项目不超过 2 个
- [ ] 标签为英文小写连字符格式，3-5 个
- [ ] JSON 格式正确，可通过 `JSON.parse()` 校验
- [ ] 文件名包含当天日期
